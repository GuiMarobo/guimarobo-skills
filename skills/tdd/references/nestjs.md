# NestJS testing guide

## Seam ladder: pick the highest seam that can observe the AC

| Seam | Use for | Setup |
|---|---|---|
| **Domain** (pure functions / domain classes, no Nest) | business rules with many cases: calculations, eligibility, state transitions | plain imports, `it.each` tables, fast |
| **HTTP module** | everything the caller sees through the API: validation → 400, auth → 401/403, status codes, serialization, wiring | `Test.createTestingModule({ imports: [FeatureModule] })` + `supertest`, real DB, boundary providers overridden |
| **Full app e2e** | cross-module flows, a few critical journeys | `AppModule` + real DB + boundaries faked |

Default split for a ticket:
- The rule's equivalence classes and boundaries → **domain** tests (table-driven).
- **One** HTTP test per AC proving the wiring, plus one per validation **class** and one per authorization rule that matters.
- Never repeat the rule's cases at HTTP level.

## Same app configuration in tests and production

`main.ts` never runs in tests, so anything it registers (`app.useGlobalPipes/Guards/Filters/Interceptors`, `setGlobalPrefix`, versioning) is missing from a `Test.createTestingModule` app. Two fixes:

- register the enhancers as providers (`APP_PIPE`, `APP_GUARD`, `APP_FILTER`, `APP_INTERCEPTOR`) inside a module the test imports (the Nest docs also recommend this when the enhancer needs DI); or
- extract one setup function and call it from both `main.ts` and the tests:

```ts
// app.setup.ts
export function configureApp(app: INestApplication) {
  app.useGlobalPipes(new ValidationPipe({ whitelist: true, forbidNonWhitelisted: true, transform: true }));
  app.useGlobalFilters(new HttpExceptionFilter());
  // ...
}
// main.ts and every e2e test call configureApp(app)
```

Otherwise tests pass while production behaves differently (or the reverse).

## Don't write these

- `it('should be defined')` stubs generated by the Nest CLI. Delete them.
- Controller unit tests with the service mocked: they test that a method calls a method.
- Service unit tests with the repository mocked: test the rule in the domain, and persistence through the HTTP seam with a real DB.
- One test per DTO decorator. Test one representative invalid input per validation class at HTTP level. Fields with a business rule get their own test.
- Tests that a module compiles or a provider is injectable: any HTTP test proves that.

## Database

- Real engine (Testcontainers or a compose test DB), migrations applied, not `synchronize`.
- Isolate tests: truncate between tests or wrap each in a rolled-back transaction.
- Build data with the project's factories or builders; create only what the test needs.

## Auth in tests

Keep **authorization** logic real. Replace only **authentication** at the boundary: sign test JWTs with a test key, or override the auth strategy to inject a known user. Every new protected route gets at least one test proving a different user/role gets 403/404.

## Async, time, queues

- `jest.useFakeTimers()` / `vi.useFakeTimers()` or an injected clock for anything time-based (`@Cron`, expirations, TTLs).
- Queue consumers: call the handler through its public method with a realistic message; assert on resulting state. Test idempotency by delivering the same message twice.
